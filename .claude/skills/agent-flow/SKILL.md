# エージェント標準編成

このリポジトリで**実装を伴う作業**を行うときの既定の進め方。

## 適用条件（重要）

全部に使わないこと。4エージェント起動は安くない。

**使う:**

- 独立した課題が2つ以上ある
- 1つでも、複数ファイル・複数モジュールにまたがる実装
- ユーザーが「エージェントを立てて」等と明示した

**使わない（自分で直接やる）:**

- typo 修正、1ファイルの数行、設定値の変更
- 調査・質問への回答のみで、コード変更が発生しない
- ユーザーが明示的に「自分でやって」と言った

迷ったら使わない側に倒し、「エージェント編成でやりますか？」と一言聞く。

## 手順

### 1. 委譲前に自分で原因を特定する

**丸投げしない。** 先に自分で該当コードを読み、可能なら再現テストを書いて
バグを実証してから渡す。診断済みの事実（file:line と再現ログ）を添えると、
エージェントが的外れな方向に走るのを防げる。

### 2. implementer を課題ごとに1体、並行起動

`Agent` ツールを1メッセージ内で複数呼び、同時に走らせる。
自分の会話コンテキストを引き継がせたい場合のみ `subagent_type: "fork"` を使う
（自分が既に深く調査した課題を続行させるとき）。それ以外は `implementer`。

各 implementer への指示に**必ず含めるもの**:

- 診断済みの原因（file:line 付き）
- やることの箇条書き（優先順位つき）
- **編集してよいディレクトリと、絶対に触らないディレクトリ**
  — 並行実行するエージェント同士のファイル範囲は排他にする。ここが唯一の衝突源
- `pnpm ci-check` を通すこと、既存テストを壊さないこと
- **コミットしない・ブランチ操作しない**（develop 直コミット禁止のため）
- CLAUDE.md 準拠（文字列リテラル直書き禁止・動的 import 禁止・TypeScript strict）
- 「落ちたテストや未着手部分を隠さず報告すること」

数値や閾値を「調整するだけ」で改善したことにされると困る箇所は、
**変更禁止・提案のみ**と明示する。

### 3. 実装完了を待つ

reviewer / security-reviewer は**差分が出揃ってから**当てる。
先に起動しても見るものがない。

### 4. reviewer と security-reviewer を並行起動

両方 `.claude/agents/` の定義を使い、1メッセージ内で同時に呼ぶ。

- `reviewer` — 実装の正しさ、既存挙動の回帰、テストが不変条件になっているか
- `security-reviewer` — 変更差分のセキュリティ影響。新規混入か既存かの切り分け

指示には**レビュー対象の差分範囲**（`git diff` の起点、変更ファイル一覧）と、
implementer の報告内容を渡す。

### 5. 指摘を反映して報告

- レビュー指摘は鵜呑みにしない。file:line を自分で確認してから直す
- 誤検知だと判断したものは、その理由を添えてユーザーに報告する
- 最後に `pnpm ci-check` の**実際の出力**で合否を示す。通っていないなら通っていないと書く

## テストの書き方

コミット 8a08ea5 で「壊れやすい AI 戦略テストを削除し、不変条件に置き換える」
という経緯がある。実装の内部挙動をそのまま写経したテストは書かせない。
「この状況では必ずこの性質が成り立つ」という不変条件で書かせること。
